### P03-D001 | pillars: operational-excellence
Scenario: Two VMs in the same VPC can't talk. You must find the blocking hop without changing any configuration. What should you run first?
A) Open a broad allow-all firewall rule and retest.
B) A Connectivity Test between the two VMs.
C) Recreate both VMs.
D) Restart the VPC.
<details><summary>Answer</summary>
B. Why: it simulates the path from your configuration and names the blocking hop.
A fails: changes security to test.
C fails: destructive, and the cause tends to sit in network config, not the VMs.
D fails: VPCs don't restart.
Verified: 2026-09-24
</details>

### P03-D002 | pillars: reliability
Scenario: All load balancer backends show unhealthy, but `curl` from another VM in the VPC gets a 200. What do you check first?
A) Firewall ingress from `35.191.0.0/16` and `130.211.0.0/22` on the health check port.
B) The application's code.
C) Cloud DNS records.
D) The backend VMs' CPU.
<details><summary>Answer</summary>
A. Why: health check probes come from those ranges; the implied deny ingress rule blocks them unless allowed.
B fails: the app answers, so code isn't the first suspect.
C fails: health checks don't use your DNS.
D fails: CPU doesn't explain healthy-from-inside, unhealthy-from-probe.

</details>

### P03-D004 | pillars: reliability

### P03-D005 | pillars: reliability
Scenario: Over a VPN, SSH to a server works but large file copies hang. What's the likely cause?
A) DNS.
B) IAM.
C) MTU: large packets are too big after encapsulation and get dropped; the peer must pre-fragment.
D) Cloud NAT port exhaustion.
<details><summary>Answer</summary>
C. Why: Cloud VPN doesn't fragment after encapsulation; small packets pass and large ones drop.
A fails: names already resolve since SSH works.
B fails: the connection is up.
D fails: the traffic isn't going through NAT to the internet.
Verified: 2026-09-24
</details>
