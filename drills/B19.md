# B19 drills

Case study: EHR Healthcare. Read it on Google's exam guide page first. Scenarios are original and paraphrase the case.

### B19-D001 | pillars: cost, reliability
Scenario: The lease on one of EHR's colocation facilities ends in five months. Most of its workloads there run fine as they are. What migration approach fits most of them?
A) Refactor every application to serverless before moving.
B) Rehost with Migrate to Virtual Machines, test-cloning each wave, and modernize after the move.
C) Rebuild the platform from scratch on Google Cloud.
D) Extend the lease and delay the decision.
<details><summary>Answer</summary>
B. Why: rehosting meets a fixed deadline; modernization can follow.
A fails: too much change for five months.
C fails: the longest path.
D fails: ignores the business decision to leave colocation.
Verified: 2026-09-24
</details>

### B19-D002 | pillars: reliability
Scenario: EHR's customer-facing app uses MySQL and must meet at least 99.9% availability. The database must survive a zone failure. What should you configure?
A) Cloud SQL for MySQL with high availability (regional): a standby in a second zone with synchronous replication.
B) Cloud SQL single-zone instance with a read replica in the same zone.
C) MySQL on one Compute Engine VM with daily snapshots.
D) Memorystore as the primary database.
<details><summary>Answer</summary>
A. Why: HA fails over to the standby in another zone and keeps committed writes.
B fails: a replica doesn't fail over on its own, and a same-zone copy doesn't survive a zone outage.
C fails: single point of failure; daily snapshots lose up to a day.
D fails: a cache, not a system of record.
Verified: 2026-09-24
</details>

### B19-D003 | pillars: operational-excellence, security
Scenario: EHR runs several Kubernetes environments and blames outages on misconfiguration. It wants consistent configuration and policy across all clusters. What should it adopt?
A) Manual reviews of each cluster every quarter.
B) One giant cluster for every customer and environment.
C) Separate teams with their own tooling per cluster.
D) GKE clusters in a fleet with Config Sync from Git and Policy Controller constraints.
<details><summary>Answer</summary>
D. Why: GitOps configuration and admission-time policy apply the same rules everywhere.
A fails: slow and misses drift between reviews.
B fails: one blast radius for everything.
C fails: the inconsistency that causes the outages.
Verified: 2026-09-24
</details>

### B19-D004 | pillars: reliability, security
Scenario: EHR's legacy file and API integrations with insurers will stay on-prem for years. Apps moving to Google Cloud must still reach them over private links, by hostname. What's needed?
A) Move the integrations to Cloud Run first.
B) Public internet calls with IP allowlists.
C) Interconnect (with HA VPN as backup) to the on-prem site, and a Cloud DNS forwarding zone for the on-prem domain.
D) VPC Network Peering to the insurers.
<details><summary>Answer</summary>
C. Why: private hybrid connectivity plus DNS forwarding lets cloud apps resolve and reach on-prem systems.
A fails: the case says these systems aren't moving now.
B fails: public exposure of health data paths.
D fails: peering connects VPC networks, not on-prem systems or external insurers.
Verified: 2026-09-24
</details>

### B19-D006 | pillars: security, operational-excellence
Scenario: EHR must keep audit logs from all projects for 6 years with consistent retention. What should it configure?
A) An aggregated log sink at the organization routing audit logs to a central log bucket with 6-year retention (lockable), or to Cloud Storage with a locked retention policy.
B) Raise `_Default` bucket retention in each project by hand.
C) Rely on the `_Required` bucket.
D) Export logs to each developer's laptop weekly.
<details><summary>Answer</summary>
A. Why: one aggregated sink covers every project, and central retention settings apply once.
B fails: manual per project and drifts.
C fails: `_Required` keeps logs for 400 days, and you can't change that.
D fails: insecure and unreliable.
Verified: 2026-09-24
</details>

### B19-D007 | pillars: security, operational-excellence
Scenario: EHR manages users in Microsoft Active Directory. It wants employees to access Google Cloud with those identities and no separate password set. What fits?
A) Create Google accounts by hand with new passwords.
B) Give everyone the same shared login.
C) Service account keys per employee.
D) Connect Active Directory to Cloud Identity by synchronizing users and groups, with single sign-on through the company's identity provider.
<details><summary>Answer</summary>
D. Why: users and groups flow from the existing directory; sign-in stays with the company's identity provider.
A fails: duplicate identities to manage.
B fails: no accountability.
C fails: keys are for workloads, not people.
Verified: 2026-09-24
</details>

### B19-D009 | pillars: operational-excellence
Scenario: New provider partners send clinical data in FHIR and HL7v2 formats. EHR wants a managed service built for those standards. What should it use?
A) The Cloud Healthcare API.
B) Firestore.
C) A custom parser on Compute Engine.
D) Cloud Storage alone.
<details><summary>Answer</summary>
A. Why: it supports healthcare standards such as FHIR, HL7v2, and DICOM.
B fails: a general document database, no healthcare standards support.
C fails: builds what the managed API provides.
D fails: stores files but doesn't understand the formats.

### B19-D010 | pillars: security
Scenario: An EHR executive says: "Google Cloud is HIPAA certified, so our workloads are compliant." Which response is accurate?
A) Correct; nothing else is needed.
B) HIPAA compliance is shared: no HHS-recognized certification exists; EHR must configure its own workloads to meet HIPAA and have a Business Associate Agreement with Google where required.
C) HIPAA doesn't apply to cloud providers.
D) Only encryption at rest is required.
<details><summary>Answer</summary>
B. Why: Google provides compliant infrastructure; the customer secures its environment and signs a BAA where required.
A fails: ignores the customer's share.
C fails: HIPAA can apply through business associate relationships.
D fails: HIPAA needs far more than encryption.
Verified: 2026-09-24
</details>
