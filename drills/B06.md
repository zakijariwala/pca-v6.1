### B06-D001 | pillars: operational-excellence, cost
Scenario: A small team with no Kubernetes experience must run 5 containerized services. It wants Kubernetes APIs but not node management. What fits?
A) GKE Standard with custom node pools.
B) Self-managed Kubernetes on Compute Engine.
C) GKE Autopilot.
D) Compute Engine VMs running Docker.
<details><summary>Answer</summary>
C. Why: Autopilot manages nodes and bills by Pod requests.
A fails: the team must manage node pools.
B fails: runs the control plane yourself.
D fails: no orchestration.

</details>

### B06-D002 | pillars: reliability
Scenario: A production GKE cluster must survive a zone outage, control plane included. What should you choose?
A) A zonal cluster with nodes in one zone.
B) A regional cluster.
C) Two zonal clusters in the same zone.
D) A zonal cluster with a bigger node pool.
<details><summary>Answer</summary>
B. Why: a regional cluster replicates the control plane and nodes across zones.
A fails: one zone.
C fails: same zone.
D fails: size doesn't add zones.

</details>

### B06-D003 | pillars: security
Scenario: Pods in GKE must read a Cloud Storage bucket. Security bans service account keys. What should you set up?
A) Workload Identity Federation for GKE, granting the bucket role to the Pod's Kubernetes ServiceAccount principal.
B) A key stored as a Kubernetes Secret.
C) Owner on the node service account.
D) Make the bucket public.
<details><summary>Answer</summary>
A. Why: Pods get short-lived Google tokens tied to their Kubernetes ServiceAccount; no key exists.
B fails: a long-lived key in the cluster.
C fails: every Pod on the node gets Owner.
D fails: public exposure.
Verified: 2026-09-24
</details>
