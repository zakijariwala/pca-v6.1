# B02 drills

### B02-D001 | pillars: security
Scenario: An auditor must read logs in a production project and nothing else. What should you grant?
A) Basic Viewer on the project.
B) A predefined logging role such as Logs Viewer.
C) Basic Editor.
D) Owner for the audit period.
<details><summary>Answer</summary>
B. Why: a predefined role scoped to logs meets least privilege.
A fails: Viewer reads every service in the project.
C fails: write access across the project.
D fails: full control.
Verified: 2026-09-24
</details>

### B02-D002 | pillars: security, operational-excellence
Scenario: The data team of 40 people changes often. How should access be granted?
A) To a Google group; manage membership in the directory.
B) To each person, updated by hand.
C) To one shared account.
D) Through service account keys per person.
<details><summary>Answer</summary>
A. Why: access follows group membership, so onboarding and offboarding are one change.
B fails: grants rot as people move.
C fails: no accountability.
D fails: keys are for workloads, and long-lived.
Verified: 2026-09-24
</details>

### B02-D003 | pillars: security
Scenario: No one except the security team may delete Cloud KMS keys, whatever roles they hold now or later. What enforces this?
A) Remove the permission from every custom role.
B) A monthly IAM review.
C) Grant the security team Owner.
D) A deny policy on the key-destroy permission for everyone except the security group.
<details><summary>Answer</summary>
D. Why: deny policies take precedence over allow grants, including future ones.
A fails: predefined and future roles still carry it.
B fails: detects after the fact.
C fails: doesn't stop anyone else.
Verified: 2026-09-24
</details>

### B02-D004 | pillars: security
Scenario: A Compute Engine VM needs to write to one bucket. How should it authenticate?
A) A service account key file on the VM's disk.
B) An attached service account with a role on that bucket.
C) The developer's user credentials.
D) A public bucket.
<details><summary>Answer</summary>
B. Why: the metadata server gives short-lived tokens for the attached service account; no key exists.
A fails: a long-lived secret on disk.
C fails: ties workloads to a person.
D fails: public exposure.
Verified: 2026-09-24
</details>

### B02-D005 | pillars: security
Scenario: A workload in another cloud must call Google Cloud APIs. Security bans long-lived credentials. What should you set up?
A) A service account key in the other cloud's secret store.
B) Basic Editor for an anonymous principal.
C) Workload Identity Federation trusting the other cloud's identity provider.
D) A VPN tunnel.
<details><summary>Answer</summary>
C. Why: the workload exchanges its own token for a short-lived Google token; no key exists.
A fails: still a long-lived key.
B fails: insecure and over-privileged.
D fails: a network path isn't authentication.
Verified: 2026-09-24
</details>

### B02-D007 | pillars: security
Scenario: Compliance says no VM anywhere in prod may have an external IP. Some admins hold Compute Admin. What enforces the rule?
A) Remove Compute Admin from everyone.
B) A firewall rule blocking ingress.
C) Ask admins not to create external IPs.
D) An organization policy constraint restricting external IPs on VMs, set on the prod folder.

### B02-D010 | pillars: security
Scenario: A user holds Owner on a project. A deny policy blocks `resourcemanager.projects.delete` for them. They try to delete the project. What happens?
A) The deletion is denied.
B) The deletion succeeds because Owner outranks deny.
C) The deletion succeeds after 30 days.
D) The deletion needs a support case.
<details><summary>Answer</summary>
A. Why: deny policies take precedence over allow policies.
B fails: allow grants can't override a deny.
C fails: the request is denied, not delayed.
D fails: not relevant.
Verified: 2026-09-24
</details>
