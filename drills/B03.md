# B03 drills

### B03-D001 | pillars: reliability
Scenario: A company will connect Google Cloud to its on-prem network, which uses parts of `10.0.0.0/8`. It's about to build production on the default auto mode network. What should it do?
A) Keep auto mode; ranges never overlap.
B) Use a custom mode VPC with ranges planned against on-prem.
C) Use one subnet per zone.
D) Use public IPs to avoid overlap.
<details><summary>Answer</summary>
B. Why: custom mode lets you pick non-overlapping ranges; Google recommends it for production.
A fails: auto mode's predefined `10.128.0.0/9` ranges may collide with on-prem.
C fails: subnets are regional, and overlap is the issue.
D fails: public exposure.
Verified: 2026-09-24
</details>

### B03-D002 | pillars: security
Scenario: A new custom VPC has no firewall rules you created. A VM in it has an external IP. Which is true?
A) Inbound SSH from the internet works.
B) All traffic both ways is blocked.
C) Inbound traffic is denied and outbound is allowed by the implied rules.
D) Outbound is blocked until you add a rule.
<details><summary>Answer</summary>
C. Why: every VPC has implied deny-ingress and allow-egress rules at priority 65535.
A fails: the implied rule denies ingress.
B fails: egress is allowed.
D fails: egress is allowed by default.
Verified: 2026-09-24
</details>

### B03-D003 | pillars: security
Scenario: The security team must block a port across every project in the organization, and project admins must not be able to override it. What should it use?
A) VPC firewall rules in each project.
B) A hierarchical firewall policy at the organization.
C) An IAM deny policy.
D) Cloud Armor.
<details><summary>Answer</summary>
B. Why: hierarchical policies apply first, and lower levels can't override their allow or deny decisions.
A fails: project admins can change them.
C fails: IAM controls API actions, not packets.
D fails: protects load balancers, not all VM traffic.
Verified: 2026-09-24
</details>

### B03-D006 | pillars: reliability
Scenario: Network A peers with B, and B peers with C. VMs in A can't reach C. Why?
A) A firewall rule in B blocks it.
B) VPC Network Peering isn't transitive.
C) Peering only works within one region.
D) C needs an external IP.
<details><summary>Answer</summary>

### B03-D008 | pillars: reliability
Scenario: With the static default of 64 ports per VM, about how many VMs can one Cloud NAT IP support?
A) 64.
B) 256.
C) About 1,000.
D) Unlimited.
<details><summary>Answer</summary>
C. Why: one NAT IP offers 64,512 ports; 64,512 ÷ 64 ≈ 1,008 VMs.
A fails: that's the per-VM port count.
B fails: a guess, not the math.
D fails: ports are finite.

</details>

### B03-D010 | pillars: reliability
Scenario: A team sizes subnets for its current 50 VMs and plans GKE clusters next year. What did it forget?
A) Nothing; GKE uses no IP addresses.
B) GKE uses the same ranges as VMs, one IP per cluster.
C) Firewall rules consume IP addresses.
D) GKE Pod secondary ranges, which consume far more addresses than VMs.
<details><summary>Answer</summary>
D. Why: each node reserves a block of Pod IPs; clusters can exhaust small ranges fast.
A fails: GKE uses a lot of addresses.
B fails: Pods take their own secondary ranges.
C fails: rules don't use addresses.

</details>
