# B17 drills

Case study: Altostrat Media. Read it on Google's exam guide page first. Scenarios are original and paraphrase the case.

### B17-D001 | pillars: operational-excellence, reliability
Scenario: Altostrat runs its content platform on GKE and keeps some Kubernetes workloads on-prem for ingestion. It wants one way to manage configuration and policy across both. What should it use?
A) Separate kubectl contexts and scripts per cluster.
B) Move all on-prem workloads to Compute Engine VMs.
C) GKE fleets, with on-prem clusters on Google Distributed Cloud, and Config Sync and Policy Controller across the fleet.
D) A second, independent GKE project per environment with no shared tooling.
<details><summary>Answer</summary>
C. Why: fleets group clusters in Google Cloud and on-prem for shared configuration and policy management.
A fails: manual per-cluster work, the opposite of consistent management.
B fails: abandons Kubernetes the case wants on both sides.
D fails: adds silos instead of central management.
Verified: 2026-09-24
</details>

### B17-D002 | pillars: performance, security
Scenario: Altostrat's on-prem ingestion site sends tens of terabytes of new media to Google Cloud each week. The site is in a building with a Google colocation facility. It needs a private, high-throughput link. What fits best?
A) Dedicated Interconnect with redundant connections.
B) One Classic VPN tunnel.
C) Uploading over the public internet with `gcloud storage cp`.
D) VPC Network Peering from the site.
<details><summary>Answer</summary>
A. Why: Dedicated Interconnect gives private, high-bandwidth links when you can reach a colocation facility.
B fails: internet-based, limited throughput, and 99.9% SLA.
C fails: public internet, no private link.
D fails: peering joins VPC networks, not on-prem sites.
Verified: 2026-09-24
</details>

### B17-D003 | pillars: cost, operational-excellence
Scenario: Altostrat wants short summaries of every new podcast and documentary with the least development effort. No labeled training data exists. What should you recommend?
A) Train a custom summarization model on Agent Platform.
B) Hire editors to write summaries.
C) Use BigQuery ML linear regression.
D) Prompt a Gemini model on Agent Platform (Vertex AI) with the transcript or media.
<details><summary>Answer</summary>
D. Why: a foundation model handles summarization with prompting; no training data needed.
A fails: needs labeled data and ML effort the requirement doesn't justify.
B fails: doesn't automate, which the business wants.
C fails: regression doesn't summarize text.
Verified: 2026-09-24
</details>

### B17-D004 | pillars: security
Scenario: Altostrat's 24/7 support chatbot is built on an LLM. Users have tried prompt injection to make it produce harmful content. What control should be added?
A) A longer system prompt telling the model to refuse.
B) Model Armor screening prompts and responses.
C) Cloud Armor WAF rules on the load balancer.
D) VPC Service Controls around the chatbot project.
<details><summary>Answer</summary>
B. Why: Model Armor inspects LLM prompts and responses for injection, jailbreaks, and unsafe content.
A fails: prompt instructions are what injection bypasses.
C fails: web attack protection, not LLM content screening.
D fails: controls data movement, not prompt content.
Verified: 2026-09-24
</details>

### B17-D005 | pillars: security, operational-excellence
Scenario: Altostrat must show that its AI content moderation decisions are auditable and explainable. Which design best supports that?
A) Let the model auto-remove content and keep no records.
B) Switch to a larger model.
C) Log each input, model output, and decision; evaluate models before release; route borderline cases to human reviewers.
D) Store only the final approved content.
<details><summary>Answer</summary>
C. Why: records, evaluation, and human review make decisions traceable and defensible.
A fails: no audit trail.
B fails: size doesn't add auditability.
D fails: drops the decisions you need to explain.

</details>

### B17-D006 | pillars: reliability, operational-excellence
Scenario: Altostrat wants modern CI/CD for its containerized services from a central platform, with safe production rollouts on GKE. What should you propose?
A) Developers build images on their laptops and push to Container Registry.
B) Cloud Build to build and test, Artifact Registry for images, Cloud Deploy with a canary strategy to GKE.
C) A cron job that runs `kubectl apply` nightly.
D) Blue/green by recreating the cluster each release.
<details><summary>Answer</summary>
B. Why: managed build, artifact storage, and progressive delivery with promotion and rollback.
A fails: Container Registry is shut down, and local builds aren't reproducible.
C fails: no testing, no gradual rollout.
D fails: heavy and slow for each release.
Verified: 2026-09-24
</details>

### B17-D007 | pillars: operational-excellence, reliability
Scenario: Altostrat mixes Cloud Monitoring with self-run Prometheus, and alerts go by email. Engineers miss incidents. What change fits best?
A) Managed Service for Prometheus to keep PromQL and exporters, with SLO burn-rate alerts routed to on-call tooling.
B) Add more email recipients.
C) Replace all Prometheus dashboards by hand before changing alerts.
D) Remove alerting and rely on dashboards.

C fails: rework that doesn't fix the missed incidents.
D fails: nobody gets paged.

### B17-D008 | pillars: security
Scenario: Altostrat employees sign in through a mix of Google identity and a third-party identity provider. They need access to Google Cloud without duplicate accounts. What should be used for the third-party users?
A) Create a second Google account for each user by hand.
B) Share one admin account among the team.
C) Service account keys for each employee.
D) Workforce Identity Federation with the external identity provider.
<details><summary>Answer</summary>
D. Why: Workforce Identity Federation lets users from an external IdP access Google Cloud with their existing identities.
A fails: duplicate accounts, the thing to avoid.
B fails: no accountability.
C fails: keys are for workloads and are long-lived secrets.
Verified: 2026-09-24
</details>

### B17-D009 | pillars: cost
Scenario: Altostrat keeps original master files of every broadcast. They're opened less than once a year, only for rights disputes, and must be kept for years. Which storage class fits?
A) Standard.
B) Nearline.
C) Archive.
D) Local SSD.
<details><summary>Answer</summary>
C. Why: Archive fits data read less than once a year; access is still in milliseconds.
A fails: pays hot-storage prices for cold data.
B fails: priced for about monthly access.
D fails: ephemeral block storage, not an archive.
Verified: 2026-09-24
</details>

### B17-D010 | pillars: performance, cost
Scenario: Altostrat wants to analyze viewing trends and give executives dashboards. Viewing data already lands in BigQuery. What's the simplest approach?
A) Export BigQuery data to a Spark cluster for analysis.
B) Analyze in BigQuery and build dashboards in Looker.
C) Copy data into Cloud SQL for reporting.
D) Write a custom dashboard app on Compute Engine.
<details><summary>Answer</summary>
B. Why: the data is already in the warehouse; Looker adds governed dashboards on top.
A fails: moves data out for no gain.
C fails: an OLTP database isn't built for large analytics.
D fails: builds what Looker provides.
Verified: 2026-09-24
</details>
