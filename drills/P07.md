### P07-D001 | pillars: reliability, operational-excellence
Scenario: A release at 14:00 causes errors for 10% of users. A rollback takes 3 minutes; a code fix will take 2 hours. What do you do first?
A) Start debugging the new code in production.
B) Roll back, then diagnose.
C) Scale up the service.
D) Post a status update and wait for the fix.
<details><summary>Answer</summary>
B. Why: restore service first when a fast, safe rollback exists.
A fails: users stay broken for hours.
C fails: capacity isn't the cause.
D fails: communicating is good, but service stays broken.

</details>

### P07-D002 | pillars: operational-excellence
Scenario: What goes in the 5-line postmortem format used in this course?
A) Timeline, blame, cost, apology, sign-off.
B) Impact, root cause, detection, fix, prevention.
C) Owner, due date, priority, status, notes.
D) Logs, metrics, traces, dashboards, alerts.

### P07-D003 | pillars: reliability
Scenario: After a marketing launch, 5% of calls from private VMs to one partner API time out. Nothing was deployed. Cloud NAT's dropped-packet metric shows `OUT_OF_RESOURCES`. What's the root cause?
A) NAT source port exhaustion.
B) A partner outage.
C) A missing firewall rule.
D) DNS failure.
<details><summary>Answer</summary>
A. Why: more connections to one destination ran the VMs out of NAT ports; that's what `OUT_OF_RESOURCES` means.
B fails: the NAT metric shows drops on your side.
C fails: a missing rule fails every call, not 5%.
D fails: DNS failure doesn't show as NAT drops.
Verified: 2026-09-24
</details>

### P07-D004 | pillars: security, reliability
Scenario: A quarterly job fails with 403. It ran fine last quarter and no code changed. What do you check first?
A) The job's container image.
B) CPU quota.
C) Admin Activity logs for changes to the job's service account, such as it being disabled.
D) Network latency.
<details><summary>Answer</summary>
C. Why: "no code changed" plus a permission error points at the identity; Admin Activity records disables and IAM changes.
A fails: unchanged.
B fails: quota errors don't return 403 permission denied.
D fails: latency doesn't cause 403.
Verified: 2026-09-24
</details>

### P07-D008 | pillars: reliability
Scenario: During a spike, a MIG stops at 24 VMs though the autoscaler wants 40. `list-errors` shows a CPU quota error for the region. What fixes it now and prevents it next time?
A) Change the autoscaler target.
B) Delete other production VMs to free quota.
C) Switch to Spot VMs.
D) Request a quota increase now; alert on quota usage and review quotas before launches.
<details><summary>Answer</summary>
D. Why: the regional quota blocks VM creation; raise it and watch it ahead of peaks.
A fails: the autoscaler already asks for more.
B fails: a short-term hack with side effects.
C fails: the error names the regional CPU quota; changing the VM pricing model doesn't raise it.
Verified: 2026-09-24
</details>
