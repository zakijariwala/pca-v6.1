# P02 drills

### P02-D001 | pillars: reliability, operational-excellence
Scenario: Three engineers run Terraform against the same network. State lives on one engineer's laptop. What should the team change?
A) Email the state file after each apply.
B) Commit `terraform.tfstate` to Git.
C) Store state in a Cloud Storage bucket with the `gcs` backend and turn on object versioning.
D) Let each engineer keep their own state.
<details><summary>Answer</summary>
C. Why: the `gcs` backend shares state and locks it during operations; versioning allows recovery.
A fails: no locking, easy to overwrite.
B fails: state can hold secrets in plain text, and Git doesn't lock.
D fails: three diverging views of one network.
Verified: 2026-09-24
</details>

### P02-D002 | pillars: security
Scenario: Terraform needs broad network permissions. Security bans service account keys. How should Terraform authenticate?
A) `credentials = file("key.json")` in the provider.
B) Impersonate a dedicated Terraform service account with `impersonate_service_account`; users hold Service Account Token Creator on it.
C) Run as each engineer's Owner account.
D) Store a key in the state bucket.
<details><summary>Answer</summary>
B. Why: short-lived credentials, no key, and the service account's roles can stay narrow.
A fails: a long-lived key.
C fails: over-privileged and tied to people.
D fails: still a key, now next to the state.
Verified: 2026-09-24
</details>

### P02-D003 | pillars: reliability
Scenario: One resource needs a field that exists only in a preview feature. The rest of the configuration uses GA features. What's the narrow fix?
A) Switch every resource to the `google-beta` provider.
B) Wait for GA.
C) Create the resource by hand in the console.
D) Declare `google-beta` and set `provider = google-beta` on that one resource.
<details><summary>Answer</summary>
D. Why: limits preview exposure to the resource that needs it.
A fails: exposes the whole configuration to pre-GA behavior.
B fails: may block the project.
C fails: creates drift outside Terraform.

</details>

### P02-D004 | pillars: operational-excellence
Scenario: A VPC network was built by hand last year. The team wants it managed by Terraform without downtime. What should it do?
A) Delete and recreate it from Terraform.
B) Write the resource in code and add an `import` block (Terraform 1.5 or later), then plan and apply.
C) Copy the network's settings into a comment.
D) Leave it unmanaged forever.
<details><summary>Answer</summary>
B. Why: import brings an existing resource under Terraform with no rebuild; `plan` previews it.
A fails: downtime for everything using the network.
C fails: not managed.
D fails: the goal is to manage it as code.
