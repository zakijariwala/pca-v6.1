### B00-D004 | pillars: reliability
Scenario: A team runs its only application VM in `us-central1-a`. It argues the app survives a zone outage because its VPC network is global. What's the flaw?
A) VPC networks are regional, not global.
B) The VM is a zonal resource; if its zone fails, the VM fails with it.
C) Firewall rules stop working during outages.
D) The subnet is zonal.
<details><summary>Answer</summary>
B. Why: resource scope sets the failure domain. A global network doesn't make a zonal VM survive its zone.
A fails: VPC networks are global.
C fails: firewall rules are part of the global VPC; the VM is the problem.
D fails: subnets are regional.
Verified: 2026-09-24
</details>

### B00-D006 | pillars: operational-excellence
Scenario: A learner installs a CLI tool into `/usr/local/bin` in Cloud Shell. The next day it's gone. Why?
A) Cloud Shell deletes tools every night on purpose.
B) Only the 5 GB `$HOME` directory persists; the VM itself is ephemeral.
C) The tool needed an API enabled.
D) Cloud Shell blocks third-party tools.
<details><summary>Answer</summary>

A fails: the reset comes from the ephemeral VM, not a scheduled deletion.
C fails: installing a binary doesn't need an API.
D fails: you can install tools, but they must live in `$HOME` to persist.

### B00-D008 | pillars: operational-excellence
Scenario: A new project was created by mistake with the wrong project ID. The team wants to rename the ID. What's true?
A) Edit the project ID in the console.
B) Use `gcloud projects update --project-id`.
C) Project IDs change on their own after 30 days.
D) The project ID is permanent once the project exists; create a new project with the right ID.
<details><summary>Answer</summary>

A fails: no tool can change a project ID, the console included.
